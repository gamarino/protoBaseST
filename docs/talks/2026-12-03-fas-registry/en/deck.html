The promise, and the only one

The same answers, the same plans and the same bytes as proto_db, on an immutable model.

It is not faster: it is several times slower, and I say so with dates. What it shows is that an immutable model is enough to be exact, bit for bit, against an implementation nobody designed for that.

Three things that are equal and checkable: the answer of every query, the planner's plan (node for node, cost for cost) and the bytes of the file. Not promised: speed, scale, production. Say it now, before someone asks.

What it is

A library: a protoST program opens a directory and is the engine

What it is

  • objects that persist reachable from named roots
  • immutable records and collections: every change answers a new version
  • named mutable cells (PBMutableObject) that a commit moves from version to version
  • perennial history: every committed version stays readable (history, snapshotAt:)
  • proto_db's disk format: format 4

What it is not

  • a product: it is a prototype for discussion
  • a server: there is no separate process and no code stored in the database
  • a new GemStone: it is in the tradition GemStone opened, not its successor
  • fast, or tested at scale

No locks in the Smalltalk layer: actors, Futures and atoms. The one lock is the operating system's flock on space.lock, the format's inter-process protocol.

The bet

Immutable values beneath a stateful language

protoCore 3.6.1

  • immutable collections that share structure
  • a mutable object is an atomic reference to an immutable snapshot
  • native threads with no global lock, a concurrent GC
  • prototypes with several parents

protoST 0.17.0

  • Smalltalk from files, no image
  • actors and Futures on native threads
  • Atom, compareAndSet:from:to: and update:with: on variables
  • classes with several parents: uses:, addBehavior:

protoBaseST 0.4.0

  • a record or a collection is a value
  • a change builds a version that shares what did not change
  • a commit publishes a new root
  • nothing in memory needs restoring on abort

protoST is not a better Smalltalk. It is your code where Smalltalk does not reach today: the same code on several cores without locks, a database shared with Python, digital twins.

Transactions

Read a snapshot, compute without effects, publish if still current

Import from: 'protobase'.
space := PBObjectSpace storage:
    (PBFileStorage path: dir pathString).
db := space newDatabase: 'hello'.
db newTransactionDo: [:tr |
    tr setRootObject: 'hits' value: 0].
db run: [:tr |
    tr setRootObject: 'hits'
       value: (tr getRootObject: 'hits') + 1].
db history size. "=> 3"

  • a transaction reads the version current when it started, for its whole life
  • every root and cell it reads enters its read set
  • at commit, if any of them changed: PBConflictError
  • run: runs the block again: the block must have no effects outside the transaction
  • blind writes of new collections merge, with Python writers too
  • granularity: roots and cells; GemStone is finer (objects)

0.2.0 · cluster

Several processes, one directory, one majority

How it works

  • a term owner (majority lease, numbered terms) grants write permissions
  • the root is built under the permission
  • commit point: synced acceptances of a majority
  • one permission at a time across the cluster

Three endings of a commit

  • committed
  • PBConflictError: nothing left the node; run: retries
  • PBOutcomeUnknownError: the root left and its fate was not learnt; run: never retries it

Evidence and cost

  • 12 simulator families, 100 to 5000 seeds; timer audit: 3420 runs, 0 violations
  • three members: 0.56× the small commits of one process; 0.33× on a hot key
  • never run on several hosts or for hours

0.4.0 · vectors

The same neighbours and the same index bytes

fsum

CPython's correctly rounded sum, ported line by line: if the scores are not identical, ties break differently and the neighbours change.

pow, not *

Python's x ** 2 is libm's pow, which rounds differently from the product. raisedTo: 2 is pow too.

k-means

proto_db's pure-Python k-means, operation for operation, with its Mersenne Twister: the same centroids, the same bytes.

  • 4021 vector-math cases, bit for bit; 101 indexes node for node
  • 'exact' and 'ivf_flat' are searched; 'hnsw' is maintained and its search refused (hnswlib's graph is not deterministic, in proto_db either)
  • the centroids equal the pure-Python training on the same C library; with numpy they may differ in the last bits, and each side validates the other's index

An honest story

The TCP node that buried actors, and a fix across three repositories

The bug (0.2.0 to 0.3.0)

In protoST an actor that waits inside a block lends its worker, which runs other actors' messages on top. A TCP reader's turn lasted as long as the connection: an actor that committed stayed buried under it until the transport stopped.

The fix (0.4.0)

  • protoBaseST: every transport turn ends after waiting at most 50 ms
  • protoST 0.16.1 (S48): a helping wait runs one message and checks its Future again
  • protoIO 0.7.1 (S49): the timeout bounds the whole write

The lesson

With helping actors, a message that never ends is not just slow: it buries whoever waits beneath it. Finite turns become a contract of every service actor.

Second part · open

The registry: from here on, the slides ask

What follows is the design of proto_db's registry, built in Python on 11/15, and a question: what it should be in Smalltalk. Nothing has been decided for protoBaseST.

Change of tone: so far I told; from here I ask. Ask people to interrupt. Write down (on the board, or in an issue afterwards) every use case that comes up.

The problem

A small ERP, several languages, and modules that extend without touching

The example

  • an ERP server with users, groups, persons and opportunities
  • the CRM module changes how a person is displayed, without editing the contacts module
  • a pricing module changes a default both rely on
  • Python and Smalltalk open the same database

Why the obvious solutions fail

  • subclasses: a stored record names its type, so a record written before the module loads with the old class
  • one dynamic class per name (Odoo): two mechanisms, methods in the class and data in the object
  • storing the code: ties the data to one language (as pickle does)
  • the module list in an ordinary root: two concurrent installs, one is lost

ProtoBase: docs/superpowers/specs/2026-11-14-runtime-registry-design.md §1 · docs/source/design-guide/registry.rst (Why the obvious solutions fail) · 22

The maintainer's requirements (11/8) come from a concrete case: a small multi-language server with users, groups, persons and opportunities, where a module extends a model without touching the base, in the manner of Odoo's _inherit. proto_db's tutorial uses partners and leads. Ask the room: how do you solve today, in Smalltalk, a package changing the behaviour of another package's class?

The spirit

A field and a method are the same thing, found the same way

One rule

o.name and o["name"] resolve alike: the object, its parents in C3 order, and finally the registry. What is found is a value or a method: data, defaults and behaviour extend by the same mechanism.

Nothing language-specific in the database

The database stores data, each object's parents and the names of the installed modules. No code, no Python classes, no import paths. Each language turns a module name into its own code.

Installs are never lost

Installing is additive and permanent. Two processes installing different modules at once both land (add-if-absent at commit).

Every error is explicit, but a miss is not an error

A name that does not exist answers None: a model gains attributes over time without breaking older objects or code (R150). What never happens: resolving silently from the wrong place.

ProtoBase: docs/source/design-guide/registry.rst (The problem) · spec 2026-11-14 §1, §2 · docs/decisions.md D62 · 23

These four requirements pull in different directions, and the design is the balance between them. The last is the most debatable for a Smalltalker: in Smalltalk a message nobody understands is doesNotUnderstand:, an error. In proto_db an attribute that does not exist is None. Leave that tension on the table: it comes back in the fundamental points.

The model, implemented in proto_db 2.0.0rc4

An instance, its catalog object, and the chain of the registry name

eva: her own attributes (name, company)

the version of tutorial.Lead's catalog object eva was created with (root __catalog)

tutorial.Lead: tut_activity's extension, then tut_crm's (newest module first)

tutorial.Partner · tutorial.Mailable · tutorial.Schedulable · tutorial.Thread, in C3 order

base: the implicit last parent of every registry name

In the database

  • each object's parents: the key p
  • __currentModules: the installed names and their dependencies
  • __catalog: one catalog object per registry name

In memory only

  • the extensions and their methods, per process
  • the registry: immutable once built

ProtoBase: docs/source/tutorials/extensible-models.rst §4, §7, §11 · design-guide/registry.rst (The choice) · 24

The catalog is a root of the database, not of the space: each database has its own. An instance lists its catalog object as a parent, so the catalog's data comes after the instance's and before the registry, with no rule of its own (Q1). An object without parents writes the format-4 record byte for byte: whoever uses none of this pays nothing. Writes never climb to a parent.

protoBaseST and the registry

Today it knows it and refuses it; adopting it is a plan the size of the cluster's

Today

  • reads formats 2 to 4, writes 4, refuses 5 with PBNotSupportedError: a database using the registry is refused at open, never misread
  • PBTypeRegistry is not this: it maps a neutral type name to a class (typeName, typeAliases)
  • no registry code written

What is normative, if adopted

  • the bytes: the key p, __currentModules, __catalog, types 22 and 23

Adapting to protoST · proposals, not decisions

Three possible shapes, each with what it costs

A · The registry as an object

  • names stay strings; a PBObject resolves through doesNotUnderstand: or an explicit resolve:
  • for: one rule for data and methods, the same as proto_db
  • against: bypasses Smalltalk's method lookup; tools see nothing; a cost per send

B · One class per name, composed at load

  • as in Odoo: each name is a protoST class assembled with the extensions as mixins, in load order
  • for: native lookup and super; browsers work
  • against: Python rejected it as two mechanisms; protoST's super is not cooperative; D21

C · protoCore prototypes

  • each object is a protoCore object whose parents are its catalog object and the registry names
  • for: the kernel already has several parents; field and method by the same lookup
  • against: which order does protoCore use? how does super reach the next extension? unverified

Proposals of this talk, for discussion · ProtoBase: spec 2026-11-14 §11 (Alternatives considered) · protoST LANGUAGE.md §4.11-4.12 · 32
