The port can comply with rc4 **without** implementing format 5. It keeps writing format 4, log
format 2 and four-item wire roots. As a format-4 reader it refuses version-5 segments, roots and
acceptor logs with `PBNotSupportedError`, and it already does so today. It must speak protocol
14, refresh its vectors to rc4, register the aliases 22 and 23, and port one new cluster rule
(the expired-permission base read, R212/R231/R233).

**Top risks.**
1. **The vector refresh breaks the harness before any product change.** `Vectors manifest`
   compares the manifest's built-in alias table with `PBTypeRegistry builtinNames`, which has
   22 names against the manifest's 24. `_referencedFiles:` (`tests/conformance/_vectors.st:98-112`)
   also refuses a database section without a string `segment`, and the new `parents_database`
   and `registry_database` sections have `segments` (a list). Every conformance runner stops at
   load.
2. **Protocol 14 is a hard gate.** A protoBaseST node still at 13 refuses every rc4 frame, and
   every rc4 message vector carries `v` 14. The cluster is protoBaseST-only (no mixed clusters),
   so in the field nothing breaks. The conformance vectors and Task 26 interop do break.
3. **R233 changes an outcome the core already decides.** The port's `roundBuildFailed:in:now:`
   (`src/protobase/cluster/holder.st:1959`) reports a failed base re-commit as *sent* unless the
   error is a conflict, validation or user error. rc4 makes "nothing sent" structural: nothing
   is sent before the re-proposal's replicate. The rc3 port reports an unknown outcome where rc4
   reports a known `none` or a retryable conflict. This is a behaviour change inside a completed
   task (Task 15), and its tests are sim tests.
4. **"Minimum" has one silent edge.** `PBAtomEnvelope decode:` (`src/protobase/framing.st:375`)
   refuses a four-key envelope as *corruption*. That is right only because the segment header
   refusal (`framing.st:85`) runs first. Any path that decodes a record without opening its
   segment header would report a valid format-5 record as corrupt instead of not supported.
   Task 30 must audit that no such path exists (opaque atoms, the atom cache, cluster records
   carried in messages: the last is ignored under CC7).
5. **Full registry support is large and mostly semantics, not bytes.** It covers the load order
   (R253–R257), C3 with oid identity (R159), add-if-absent merge at commit, catalog
   replacement, the `base` module and the mismatch rules. It is not part of the cluster plan,
   and putting it there would double that plan's risk.

### 2.1 FORMAT

**F1. `FORMAT_VERSION` 5, write version still 4, feature versions.**
- *proto_db:* `storage/format.py:51` `FORMAT_VERSION = 5`; `:57` `WRITE_FORMAT_VERSION = 4`;
  `:61` `FEATURE_VERSIONS = {"parents": 5, "registry": 5}`; `:152`
  `READABLE_FORMAT_VERSIONS = {2,3,4,5}`. FS lines 36-48 (version table) and 114-135 (a
  segment's version is that of its first record; a root's version is the highest of 4, the
  root it replaces and what its writer wrote). Rulings R151 and R242; D62.
- *Impact:* a format-4 reader that writes no feature is compliant. The port refuses version 5
  at the segment header (`src/protobase/framing.st:85`, `between: 2 and: 4`) and at the root
  record (`framing.st:261`) with `PBNotSupportedError`, which is exactly the rc4 rule for a
  reader that predates 5. It writes version 4 everywhere (`framing.st:220`). No code change.
- *Where:* docs only. `docs/deviations.md` "Reading" (line 217) should say format 5 exists and
  protoBaseST reads 2–4 and refuses 5. Do it in the new Task 21a (section 4).
- *Size:* S.

**F2. Per-record segment versioning (R151).**
- *proto_db:* a record needing version v goes to a segment of at least v, rolling the segment
  otherwise. `storage/file.py:362-376` (`_reserve`, `seg.version < version`), `:346`

  features=)`, declared features must equal the payload's), `:74` (`written_version`);
  `storage/format.py:75` `payload_features`, `:94` `atom_version`, `:141` `framed_version`.
- *Impact:* none while the port writes no feature. Full format-5 writing needs it.
- *Where:* registry plan (section 3b).
- *Size:* M.

**F3. Root record version carried, never lowered.**

**F5. Built-in type aliases 22 and 23.**

**F6. `parents` and `with_parents` are reserved names for new fields (R157, R158).**
- *proto_db:* FS "Reserved names" (from format 5: a writer MUST NOT create such a field and keeps

### 2.2 WIRE

**W1. `PROTOCOL_VERSION` 14.**
- *proto_db:* `cluster/protocol.py:184`. Protocol 14 means records carried by `replicate`,
  `records`, `store`, `warm` and `fetched` may be format 5, and a receiver writing records into a
  segment it did not create writes the version of the segment's first record. 13 and 14 must not
  mix. CP "Messages (protocol version 14)".
- *Impact:* `PBClusterMessage class >> protocolVersion` (`src/protobase/cluster/protocol.st:95`)
  becomes 14, and the "13.0 is version 13" float rule follows. Speaking 14 without format 5 is
  consistent:
  - the port never writes peer records into segments (DEPTH = 0 over shared storage; CC7 ignores
    `records`, `store`, `warm` and `fetched`);
  - a five-item root of version 5 is refused (W4).
- *Texts to update:* `errors.st:28` (`PBClusterProtocolError` comment),
  `tests/unit/cluster_messages.st` (lines 2, 13, 23, 69, 72, 127, 129, 136; the ported row
  `test_cluster_protocol.py::test_replicate_no_longer_carries_pred_committed` now asserts 14),
  `tests/conformance/messages.st:46`, deviations "Cluster wire messages" (`v != 13`) and CC4
  ("Disabled, the frames are protocol 13 byte for byte"; the plan's CC4 row too), reference,
  tutorial.
- *Where:* follow-up to Task 5 (completed), carried out in Task 21a.
- *Size:* S.

**W2. Optional `unknown` on `fetched` and `commit_info` (R240L, R243L, R244L).**
- *proto_db:* `cluster/protocol.py:244` `OPTIONAL_FIELDS`, `:306` (checked when present, a bool;
  absent reads false); FS line 1801.
- *Impact:* the port decodes and validates these two types and then ignores them (CC7). It must
  add an optional-field table: absent is accepted, present and not a Boolean is
  `PBClusterProtocolError` (drop), and any other unknown key stays ignored as today. The vector
  `fetched-unknown.frame` exercises it. *Answering* with `unknown` belongs to the fetch service,
  which is Phase D (N2).
- *Where:* Task 5 follow-up, in Task 21a.
- *Size:* S.

**W3. Acceptor log format 3 and versioned entries (kind 7).**
- *proto_db:*
  - `storage/logfile.py:79` `LOG_FORMAT_VERSION = 3`, `:83` `LOG_WRITE_VERSION = 2`, `:85`
    `READABLE_LOG_VERSIONS = {2,3}`;
  - `cluster/rootlog.py:161` `VERSIONED_KIND = 7`, `:168` `VERSIONED_LOG_VERSION = 3`, `:252`
    `_versioned`, `:260` `_unwrap`, `:289` `_records_version`, `:655` (the header is raised in
    place, fsync-ed, before the first versioned entry); compaction writes 3 only while it keeps
    one;
  - FS line 1575 (header) and 1677 (kind 7: `kind u8 | storage format u16 | entry of kind 1, 2, 5
    or 6`; a version ≤ 4, another wrapped kind or a short entry is corruption; an unreadable
    version is not supported).
- *Impact at minimum:* the port writes log format 2 (it never writes a v5 root), which rc4
  requires for every log without a versioned entry. `PBFramedLog scan:kind:path:`
  (`src/protobase/cluster/log.st:183`) refuses any header version other than 2 with
  `PBNotSupportedError`, which is what rc4 states for a reader of log format 2 ("refuses such a
  log at its header"). The port's `PBAcceptorLog` would refuse kind 7 as an unknown kind
  (corruption), but the header check runs first, so that path is never reached. No code change.
  The `roots_log_v5` vector becomes an expected `PBNotSupportedError` (F7), and `log-version-4`
  is refused as before.
- *Impact in full support:* read headers 2 and 3; decode kind 7, carrying the version into
  `PBRootRecord`; write kind 7 for a root or records above 4; raise the header in place with
  fsync before the first such entry; compaction keeps 3 only while one remains.
- *Where:* minimum is docs and vectors in Task 21a. Full support is a follow-up to Task 4
  (completed) in the registry plan.
- *Size:* S (minimum) / M (full).

**W4. Five-item wire root `[epoch, segment, offset, label, version]`.**
- *proto_db:* `cluster/protocol.py:373` `encode_root` (fifth item only when the version is above
  4); `:389` `decode_labeled_root` (5 accepted; a fifth item ≤ 4 is malformed; an unreadable
  version is `ClusterProtocolError`); FS line 1739.
- *Impact at minimum:* the port's `_rootProblem:` (`protocol.st:259`) refuses any length other
  than 3 or 4. For a format-4 node every five-item root is refused either way: version ≤ 4 is
  malformed, 5 is unreadable. The behaviour is the same and only the text differs. The cheap
  alignment is to accept length 5 syntactically and refuse with `proto_db`'s two reasons, so that
  full support only widens the readable set.
- *Where:* Task 5 follow-up in Task 21a. The full encoding goes to the registry plan.
- *Size:* S.

## 3. The runtime registry (format 5: `parents`, `registry`; D62)

### 3a. Minimum rc4 compliance without the feature

A port may stay a format-4 writer indefinitely. FS "Format stability" states that data without a
feature keeps version 4, and that a reader that predates *n* refuses *n* with
`ProtoNotSupportedError` and never misreads it. What the port must do:

1. **Segments and roots of version 5: refuse with `PBNotSupportedError`.** This is already done
   (`framing.st:85`, `:261`). Keep `between: 2 and: 4`. A space that any rc4 writer opened with a
   feature has a version-5 root (R242), so the port refuses the whole space at open. That is the
   intended, conservative behaviour. Audit (Task 30) that no record is decoded without its
   segment header having been checked (risk 4).
2. **Acceptor log format 3: refuse at the header with `PBNotSupportedError`.** This is already
   done (`cluster/log.st:183`). Keep writing log format 2, which rc4 requires for any log without
   a versioned entry. The port never writes kind 7, and it must not "read v3 and ignore kind 7":
   that would read format-5 roots as format 4, which the format forbids.
3. **Protocol 14 handshake.** There is no negotiation: every message carries `v`, and anything
   other than 14 drops the connection. Required changes: `protocolVersion` 14 (W1); `unknown`
   optional and checked (W2); five-item roots refused with `proto_db`'s reasons (W4). A 13 node
   and a 14 node never form a cluster, which the CHANGELOG states as intended.
4. **Keep writing format 4.** Yes, this is allowed indefinitely. Nothing else in format 4 changed:
   every rc3 vector of version ≤ 4 is byte-identical except the renamed invalid files.
5. **Name reservations and aliases.**
   - Register aliases 22 and 23 by name with no class (F5).
   - Refuse creating fields `parents` and `with_parents` while still reading them (F6).
   - Refuse `removeRootObject:` of `__` names (S1).
   - Never write `__currentSymbols`. The port already refuses every `__` write.
6. **Vectors.** Re-vendor rc4. Teach the harness the `segments` list. Record `parents_database`,
   `registry_database` and `roots_log_v5` as expected `PBNotSupportedError` refusals (F7).
7. **Docs.** Deviations "Reading" names format 5 as refused, with the reason (the registry is a
   separate plan).

*Size of the minimum:* S–M in total (Task 21a), about 1–2 days.

### 3b. Full support of `parents` and the registry in Smalltalk

**What becomes of Python modules.** A `proto_db` module is an importable Python module that
calls `module(name, depends=...)` and declares `@handle.extends(registry_name, parents=...)`
container classes. In protoBaseST a registry module would be a **protoST module** (a `.st` file
loaded with `Import from:`). It declares a `PBRegistryModule name: 'crm' depends: #('base'
'contacts')` and its extensions as **extension objects**. An extension holds a registry name, a
`parents` tuple (registry names only, Q6), method blocks or `CompiledMethod`s keyed by selector,
and canonical data defaults. Its methods, like Python's, are never persisted.
- The language-neutral module *name* is what the database stores. Mapping a name to a protoST
  module path is the port's own job (Python's `modules_mapping` analogue).
- Each language ships its own version of each module ("Methods are per language", design guide).
  The port must also ship its own `base` module (FS "Registry roots": every runtime provides
  `base`).

**Python-specific (choose freely):**
- the import mechanism, the module-name-to-path mapping and `modules_allowed`;
- how `_super` finds its position: Python uses the caller's code object (Q3, R239); Smalltalk can
  use `thisContext` sender method identity or an explicit cursor passed in the call;
- the refusal rules for properties, staticmethods, lambdas and nested classes (Q4 maps to "plain
  methods and canonical data only");
- `ModulesBeingImported` (R234), `__getitem__`/`KeyError` (R238), the Django fallback,
  `functools.wraps` (R239);
- the process-global module-name rule (R167) and reload (R168);
- the process cache keyed by module set (R257: keep the key a set, which is a semantic
  requirement, but the cache itself is the port's);
- `read_data_file` path hardening (R206): the port needs an equivalent containment rule for its
  own `base`, but the mechanism is OS-specific;
- the Python-member-hides-definition refusal (R240): its analogue is a `PBObject` subclass method
  hiding a registry selector.

**Format the port must follow byte for byte:**
1. **Envelope `p`** (F4): the four keys in order `t, oid, s, p`; a non-empty `@tup` of `@ref`s
   and non-empty strings; no duplicates; only on DBObject or opaque records; a parentless object
   writes the three-key record byte for byte. Refuse an object that is its own parent.
2. **Feature versioning** (F2, F3): a record with `p` or a type tag 22/23 opens a version-5
   segment; a segment's version is its first record's; a root's version is the max of 4, the
   replaced root and what the writer wrote (R242); never lowered.
3. **Cluster** (W3, W4, C4): kind-7 entries and log format 3 raised in place with fsync; the
   five-item wire root; the version excluded from root identity; the persister's republish of
   the same root at a higher version.
4. **`ModuleList` (alias 22)**: `modules` is a `@tup` of `(name, depends)` 2-tuples, a name
   appears once, anything else is corruption. **`Catalog` (alias 23)**: `entries` is a ref to a
   `Dictionary` from registry name to a DBObject whose parents include that name (`proto_db`
   writes exactly the one-name tuple). Both carry no `p`. Roots are identified by name **and**
   type: a `__` root of another type is `PBCorruptionError` (FS "The per-database class
   registry").
5. **Writer rules**: append only to `modules`; `base` first; a list that does not start with
   `base` is written with `base` first on the next append (R235); catalog entries added only if
   absent, never removed, replaced only by a new version of the same catalog object (new oid,
   parents still include the name; R189, R190).

**Semantics the port must follow (FS normative, or required for cross-language agreement):**
1. **Load order (R253–R257, FS "The load order", MUST):**
   - `base` first explicitly (R255);
   - then repeatedly the smallest-named module whose dependencies are all placed, in code-point
     order (R254). In protoST, compare the UTF-8 bytes or the code points, never a
     locale-sensitive or UTF-16 comparison;
   - the dependencies are the ones the module's *code* declares at load time, not the persisted
     `depends` (that field is a record of the install);
   - a cycle or an unlisted dependency is an error;
   - the persisted order decides nothing (R256);
   - extensions chain newest-loaded-first, and a name's parents are the union of its extensions'
     `parents=` in load order.
2. **Lenient read of the list (R235, MUST):** treat `base` as first when the list does not start
   with it; an empty list lists nothing.
3. **Resolution: C3 linearization** (`proto_db/resolution.py`; design spec section 5; design
   guide "C3 over depth-first"):
   - own attributes first, then the C3 order of the parents;
   - object nodes contribute their own fields;
   - registry-name nodes contribute their extension chain, newest first;
   - `base` is the implicit last parent of every registry name (R204);
   - nodes are identified by oid, and the first met in a left-to-right depth-first walk is used
     (R159); parent cycles are refused (R160);
   - a name no module extends is an empty node (R171 overturned);
   - a miss answers nil, and `includes:` tells absence from an explicit nil (R150);
   - writes never climb the parents.

   FS calls resolution "behaviour, not format", and the design spec lets "Smalltalk resolve by its
   own rules". **Recommendation:** implement C3 exactly anyway. Data defaults and catalog data are
   shared across languages, and only an identical linearization makes `o.x` answer the same data
   in both runtimes, which is D62's stated goal ("protoBaseST must compute the same registry from
   the module set alone").
4. **Roots `__currentModules` and `__catalog`:**
   - `installModule:` adds the module, its missing dependencies and `base` (first, R205);
   - it creates a catalog object (a DBObject with parents `(name)`) for each newly introduced
     registry name;
   - **at commit, under the root lock, it merges add-if-absent against the roots current at
     commit**, never the snapshot's, never through the read set (`transactions.py:2959`
     `_merged_registry`), so concurrent installs never conflict;
   - a merged union that cannot be built is a retryable `PBConflictError` naming the concurrent
     modules (review N-4);
   - `installedModules` and `catalogObject:` never enter the read set, while `getRootObject:` of
     a registry root does (R241);
   - `setCatalogObject:` conflicts by normal rules (the first updater wins, R189).

   In the port this lands in `PBTransaction`'s commit build (`_buildOn:`) and therefore runs
   inside `publishGroup:` (Task 22) and `PBClusterRound` builds (Task 23) alike.
5. **`removeRootObject:` and `setRootObject:` refuse `__` roots** (S1); only the registry writes
   them.
6. **Mismatch and binding (Q2, R201, R236, R243):**
   - the code doing the resolving decides the registry: the object's transaction, else the
     current reader, else the space's single list, else an error;
   - a database listing no modules resolves with no registry, and reaching a name node there is
     `PBNotSupportedError` "needs a registry";
   - another process's install makes the next lookup of an old-bound space fail with
     `PBValidationError`, with no automatic rebuild; `reloadRegistry:` is the explicit rebuild;
   - snapshots resolve with their own version's list;
   - a listed module that cannot be loaded is `PBNotSupportedError` at the first lookup that
     needs it.
7. **API reservations:** `parents` and `withParents:` become constructor and API names; `parents:`
   with a non-tuple is refused (R158 analogue); index keys and query paths read own attributes
   only.

**Rough size: L.** Roughly 3–4 weeks of plan-driven work, comparable to the cluster plan's
Phase A plus B:
- format writing (F2, F3, envelope, aliases, vectors fully read): M, about 4–5 days;
- cluster carriage (kind 7, log format 3, five-item roots, persister): M, about 3 days, and best
  after Task 30;

- modules, load order, `base`, `_super` in protoST: M–L, about 5 days;
- install, merge and catalog at commit, mismatch rules: M, about 4 days;
- porting `test_registry_*`, `test_resolution.py`, `test_dbobject_parents.py` and
  `test_format_features.py` (about 5 600 lines of Python tests) and the two concurrency suites:

It needs its own spec and plan (it is not a cluster task) and the maintainer's answers on the
